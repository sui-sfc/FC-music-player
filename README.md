# FC Music Player

普通の音楽を、ファミコン音源 (2A03 APU) の音にリアルタイム変換するブラウザアプリです。

## 起動

```bash
node server.js
```

ブラウザ (Chrome / Edge 推奨) で http://localhost:8080 を開きます。

### 入力ソース
- **ファイルを開く**: mp3 / wav / m4a など
- **テスト音源**: 内蔵のデモ曲 (動作確認用)
- **テスト音源(歌)**: 中央に歌っぽい声、左右に伴奏を置いたデモ (ボーカルモードの確認用)
- **マイク**: ヘッドホン推奨 (ハウリング防止)
- **タブ/システム音声**: YouTube や Spotify などを変換。共有ダイアログで「音声を共有する」にチェック。タブ共有なら元の音は自動でミュートされます。

## 仕組み

```
入力音声 ─→ [driver.js] 解析 ─→ APU レジスタ書き込み ─→ [apu.js] 2A03 エミュレート ─→ 出力
              (60Hz / フレーム)       ($4000-$400F)
```

| チャンネル | 役割 | 解析 (AI 解析 ON のとき) | 解析 (内蔵) |
|---|---|---|---|
| 矩形波1 | メロディ (歌) | RMVPE の音程 → 先読みビタビ | ステレオ中央成分 + 倍音加算 → 先読みビタビ |
| 矩形波2 | 楽器の旋律 (既定) / コードのアルペジオ / ハモリ / エコー | 楽器の旋律: Basic Pitch の音符から歌・ベース以外の中音域の楽器を先読みビタビで 1 本に。アルペジオ: コード認識 | コードの構成音を 1 つ静かに伸ばす |
| 三角波 | ベース (+ キック時のピッチスイープ) | Basic Pitch の低音 → 先読みビタビ、弾き直しで 1 フレーム区切る | スペクトルのピーク |
| ノイズ | ドラム | 調波・打撃音分離 (HPSS) → 帯域ごとの立ち上がり → キック / スネア / ハイハット | 同左 |

- **メロディの担当**: 歌があれば歌、歌の無い区間 (イントロ・間奏) はリード楽器 (シンセやギターの旋律) を矩形波1で鳴らす。
  RMVPE は楽器の旋律も拾うため、先読み区間の確信度の平均が低い (0.25 未満) ときは「歌ではない」とみなしてリード楽器に切り替える
- **オクターブ**: フレーズの頭で、その音程の中央値が C5 付近に来るほうを選ぶ。男性ボーカルなど低い歌は 1 オクターブ上げる (ファミコンアレンジの定番)
- **コード認識**: メジャー / マイナー / パワーコード (ルート+5度) の 36 種 + コード無し。先読み区間全体で最もつじつまの合うコード進行を選ぶので、一瞬の誤判定で和音がバタつかない
- **アレンジ**: メロディは既定で「ファミコン風」: 音程を半音に固定し、先読みで 4 フレーム以上続く音だけを新しい音にする (しゃくり・すべりで細かい音が出ない)。伸ばした音にだけ 0.3 秒後から一定のビブラート (±15 セント, 6Hz)。歌はオクターブを上げず、デューティ比 25% (聴き比べで決定)。音の出だしに音量アクセント → ゆっくり減衰。矩形波2 は既定で「楽器の旋律」: 原曲のギター・シンセなどが弾いている音を拾い、音をなるべく変えずに 1 音ごとに減衰させて鳴らす。歌 (矩形波1) と同じ音・半音違いの音は避ける。楽器が見つからない所はコードの構成音を静かに伸ばす (「楽器の旋律の落ち着き」で音の変わりやすさを調整)。従来の 1 フレームごとに切り替えるアルペジオも選べる
- **編曲 (`worklet/arranger.js`)**: 「変換」から「アレンジ」に近づけるための判断
  - **奏法**: 矩形波1 の音の出だしは半音の半分だけ上からしゃくり下ろし (「出だしのしゃくり」)、最初の 2 フレームだけデューティ比を 50% にして太く (「出だしの音色」)。音の終わりはすぐ切らず、12.5% で小さく 4 フレーム残す (「音の余韻」)
  - **テンポ**: ドラムの立ち上がりの強さを自己相関してテンポを、その周期で櫛形に足し合わせて拍の位置を推定 (Get Wild 132 BPM, なんもねえ 166 BPM)。倍・半分への揺れは無視する
  - **場面 (静か / 普通 / サビ)**: 音圧のそろった最近の曲は全体の音量ではサビが分からない (Get Wild で 0〜3dB) ので、「歌の大きさ」(サビは声を張る) と「ドラムが鳴っているか」で判定。
    歌がこれまでで一番大きい所から 1.5dB 以内ならサビ (聴き始めて 30 秒後から)。入るのは 2 秒、抜けるのは 4 秒続いたら
  - **編成を場面で変える** (矩形波2 = 「自動」): 静か = 楽器の旋律を控えめに、普通 = 楽器の旋律、サビ = 拍に合わせたアルペジオ (32 分音符, 1-3-5-3。歌より上に出る音は 1 オクターブ下げる。聴き比べで 16 分より 32 分)
  - **ベースの刻み** (「ベースの弾き方」): 静かな場面以外は、原曲のベースの音を 8 分音符で刻み、裏拍を 1 オクターブ上に跳ねる (ファミコン曲の定番。聴き比べで採用)。拍の頭で 1 フレーム切って弾き直す
  - **メロディを拍に揃える** (既定 OFF): 音の切り替えを 16 分音符の区切りまで待つ。聴き比べでは採用せず
- **ドラム**: スペクトログラムで時間方向に伸びる成分 (伸ばした音) と周波数方向に伸びる成分 (打撃) を中央値フィルタで分け、打撃成分だけで判定。強さに応じて音量も変える
- 実機と同じ形式でレジスタを書き込み、APU エミュレーターが音を合成

### ボーカルモード (既定 ON)
歌声は「ビブラートで音程が揺れる」「倍音が強くオクターブを誤りやすい」「伴奏と混ざる」ため、専用の処理をしています。

1. **ステレオ中央成分の抽出**: 左右で大きさ・位相が揃った成分だけを取り出してメロディ解析に使う (ボーカルはほぼ必ず中央定位)。ビブラートでにじまないよう歌用は短い窓 (85ms) で解析し、伴奏と重なりにくい高めの倍音まで 10 本使う
2. **メロディの連続追跡**: 候補を「顕著度 × 音程の揺れ (歌はビブラートで揺れ、ギターはほぼ揺れない) × 声域の中心への近さ × 直前の音程への近さ」で選ぶ。奇数倍音が伴奏に埋もれて 1 オクターブ上に見える場合に備え、1 オクターブ下も候補に入れる。大きな跳躍は数フレーム続いたら採用し、発声していない区間は無音に
3. **先読み (既定 0.5 秒)**: 出力を少し遅らせ、未来のフレームまで見てから「最もつじつまの合う音程の経路」をビタビ法で決める。
   その場その場で決めるより、音のバタつきや一瞬の誤検出が大幅に減る。ファミコンの音だけを聴く使い方なら遅れは問題にならない
   (「先読み」「音の落ち着き」スライダーで調整可)
4. **ピッチベンド出力**: 半音に丸めず、倍音のピーク位置から求めた実際の音程で矩形波の周期 (11bit) を設定。ビブラートやしゃくりがそのまま再現される

楽器だけの曲やモノラル音源では、OFF にしたほうが安定することがあります。

処理はすべて AudioWorklet 内で行うので、タブがバックグラウンドでも途切れません。

## 開発用ツール (オフライン変換)

ブラウザと同じ変換エンジン (`worklet/engine.js`) を Node で動かし、曲の一部をまとめて変換して結果を確認できます (15 秒を約 0.5 秒で処理)。ffmpeg が必要です。

```bash
node tools/devtest.mjs <音声ファイル> --start 0 --dur 15
```

`dev-out/` (git 管理外) に出力します。
- `roll.png`: 上段 = 中央成分のスペクトル + メロディ (赤) と倍音のはしご (ピンク)、下段 = 全体のスペクトル + 全チャンネル。
  ピンクの点が歌の揺れる倍音の線に重なっていれば、メロディは正しく追えています
- `chip.wav` / `orig.wav`: 変換後と元の音
- `--set vocal=false` のようにパラメータを変えて比較できます
- `--ai` を付けると AI 解析 (RMVPE + Basic Pitch) を使います (下記)。コード進行とベースラインも表示します

### リアルタイム版の精度の測り方

`tools/stream-sim.mjs` はブラウザの音源分離モードと同じ区切り方 (`worklet/stemstream.js` を共有) で Node 上で変換する。
「曲全体を一度に分離・解析したオフライン版 (htdemucs_ft)」を目標にして、`tools/cmp-frames.mjs` で一致率を出す。

```bash
.tools/venv/Scripts/python.exe tools/separate.py 原曲.flac dev-out/sep/x_ft 0 75 htdemucs_ft
node tools/devtest.mjs 原曲.flac --dur 70 --ai --stems dev-out/sep/x_ft --out dev-out/sim/best
node tools/stream-sim.mjs 原曲.flac --dur 70 --model ft --hop 2 --out dev-out/sim/rt
node tools/cmp-frames.mjs dev-out/sim/best/frames.json dev-out/sim/rt/frames.json
```

Get Wild 冒頭 70 秒 (目標 = オフライン htdemucs_ft):

| | メロディ 音程 | 発声の一致 | ベース 音程 | ドラム |
|---|---|---|---|---|
| 分離なし (AI 解析のみ) | 82% | 75% | 62% | 36% |
| リアルタイム htdemucs (Basic Pitch の修正前) | 89% | 89% | 81% | 72% |
| リアルタイム htdemucs | 90% | 91% | 93% | 72% |
| **リアルタイム htdemucs_ft (既定)** | **91%** | **93%** | **94%** | **87%** |

- **Basic Pitch の窓のつなぎ方の修正**: 1 窓 142 フレームを窓の間隔 (141.27 フレーム) と無関係に並べていたため、窓ごとに約 8.5ms ずつ遅れ、60 秒で約 0.3 秒ずれていた (公式実装と同じ並べ方)。
  フレームを本当の時刻の位置に置くように直した。オフライン解析のベース・コードが曲の後半ほど遅れていたのが直り、参考アレンジとの一致もメロディ音名 53→56%、ベース 59→62% に
- 試して効果が無かったもの: 右の余白・左の文脈を長くする、ベースを RMVPE (単音) で推定 (ほぼ同じ結果。残してある)、低いベースを 1 オクターブ上げる (参考と大きくずれる)

| | メロディ: 比較点数 | 音程一致 | 音名一致 | ベース 音程一致 | 音名一致 |
|---|---|---|---|---|---|
| リード楽器・オクターブ調整なし | 126 | 33% | 56% | 40% | 63% |

#### 音の調整 (参考アレンジとの測定から)
- `tools/balance.mjs`: 帯域ごとの音量バランスを比べる
- 全体の音量を +5dB (ソフトクリップ付き)、DPCM キックを控えめに、ハイハットのノイズ周期を index 3 に
  (index 1 だと音の大半が可聴域の外に出てしまう)
- メロディは 1 音ごとに「出だしが最大 → 約 0.3 秒で半分」の減衰 (参考の 75 音の平均の形に合わせた。「音の減衰」で調整)
- 参考のリードのデューティ比は倍音の並びから 50% (静かに伸ばす場面だけ 12.5%) と推定 → 既定値 50% のまま
- 参考の高音域が明るいのはハイハットではなく、録音したエミュレーターのフィルターが実機より明るいためと判断 (実機寄りのまま)

### AI 解析 (RMVPE + Basic Pitch)

| モデル | 役割 | サイズ | 速度 (開発 PC) |
|---|---|---|---|
| RMVPE | 伴奏入りの曲から歌の音程を推定 | 362MB | 1 秒あたり約 17ms |
| Basic Pitch (Spotify) | 鳴っている全ての音符 (和音・ベース) と立ち上がりを推定 | 230KB | 2 秒あたり約 10ms |

準備:

```bash
npm install
curl -L -o models/rmvpe.onnx https://huggingface.co/lj1995/VoiceConversionWebUI/resolve/main/rmvpe.onnx
curl -L -o models/basic-pitch.onnx https://raw.githubusercontent.com/spotify/basic-pitch/main/basic_pitch/saved_models/icassp_2022/nmp.onnx
```

- 前後処理は `worklet/rmvpe.js` と `worklet/basicpitch.js` (環境に依存しない純粋な JS)。Node でのモデル実行は `tools/*-node.mjs`
- **ブラウザ**: 「AI 解析」にチェックを入れると有効 (`node server.js` で起動したときのみ。モデルの読み込みに数秒)
  - AudioWorklet が 16kHz / 22.05kHz に落とした音声を 0.25 秒ごとに Web Worker (onnxruntime-web, マルチスレッド WASM) へ送って推論
  - 結果は時刻つきで AudioWorklet に返し、先読み中のフレームに差し込む。推論窓の端は精度が落ちるため、ON にすると先読みを 1 秒にする
  - 推論時間: 両モデル合わせて 0.25 秒ごとに約 140ms (開発 PC)。出力の遅れは約 1 秒
  - 曲全体を一度に推論するオフライン版とのメロディ一致率は約 86%、コード進行・ドラム数もほぼ同じ
- **オフライン**: `node tools/devtest.mjs <file> --rmvpe`

### 音源分離 (Demucs)

Meta の Demucs (htdemucs) で曲を **歌・ベース・ドラム・その他の楽器** の 4 つに分けてから解析します。

| 分離した音 | 使い道 |
|---|---|
| 歌 | RMVPE と歌の音程解析 (中央成分の抽出の代わり) → 矩形波1 |
| ベース | Basic Pitch で採譜 → 三角波 |
| その他の楽器 | Basic Pitch で採譜 → 矩形波2 の「楽器の旋律」と、歌の無い所のリード |
| ドラム | ドラム検出 → ノイズ / DPCM |
| ドラム以外 | 音程の解析 (スペクトル) |

準備 (Python を `.tools/` に入れる。GPU 不要):

```bash
curl -L -o .tools/uv/uv.zip https://github.com/astral-sh/uv/releases/download/0.5.11/uv-x86_64-pc-windows-msvc.zip   # 展開して uv.exe
UV_PYTHON_INSTALL_DIR=.tools/python .tools/uv/uv.exe venv --python 3.11 .tools/venv
.tools/uv/uv.exe pip install --python .tools/venv/Scripts/python.exe torch torchaudio --index-url https://download.pytorch.org/whl/cpu
.tools/uv/uv.exe pip install --python .tools/venv/Scripts/python.exe demucs soundfile
```

使い方:

```bash
.tools/venv/Scripts/python.exe tools/separate.py 原曲.flac dev-out/sep/x        # 曲の頭から分離 (vocals/bass/drums/other.wav)
node tools/devtest.mjs 原曲.flac --dur 60 --ai --stems dev-out/sep/x
```

- 速度: CPU (16 スレッド) で実時間の約 0.2 倍 (4 分の曲を 46 秒)。リアルタイムにも間に合う速さ
- 効果 (分離なし → あり):
  - なんもねえ 冒頭 60 秒: 歌の 7 半音超の跳躍 19 → 1 回、オクターブ跳躍 7 → 0 回。誤検出のキックが減り (166 → 122)、スネアは増えた (68 → 79)
  - Get Wild 冒頭 66 秒 (参考アレンジとの比較): ベースの音程一致 41% → 51%。メロディ (矩形波2 を消して比較) は比較点 374 → 447、音名一致 51% → 57%
  - Get Wild 全曲: メロディが鳴っている割合 54% → 74% (歌の無い所でシンセの旋律を拾えるようになった)。そのぶんリードの跳躍は増えた (リフのオクターブ跳躍を含む)
#### ブラウザ (リアルタイム)

「音源分離 + AI 解析」にチェックを入れると有効 (「AI 解析」とはどちらか一方)。

```bash
.tools/venv/Scripts/python.exe -m pip install onnx onnxruntime   # (uv pip でも可)
.tools/venv/Scripts/python.exe tools/export-demucs.py models/htdemucs.onnx   # 174MB の ONNX を作る
node tools/demucs-node.mjs --check   # JS の前後処理が PyTorch と一致するか検算
```

- STFT / 逆 STFT は ONNX にしにくいので外に出し (`worklet/demucs.js`)、ネットワーク本体だけを ONNX にした。PyTorch との差は最大 0.002 (-43dB)
- `demucs-worker.js`: 入力を 44.1kHz で貯め、1 秒ごと (GPU) / 3 秒ごと (CPU) に直近 7.8 秒の窓で分離。
  窓の右端 1 秒は精度が落ちるので使わず、その手前の 1 秒ぶんだけを出す (つなぎ目は 50ms 重ねる)。
  同じ Worker で 歌 → RMVPE、その他の楽器・ベース → Basic Pitch も実行して、分離した音と一緒に AudioWorklet へ返す
- AudioWorklet (`Engine.processLive`): 入力を貯めておき、分離結果が届いた区間から 8 倍速で変換して、決まった時間だけ遅らせて出力。
  足りなくなったら遅れを 0.25 秒ずつ自動で延ばす
- 速度 (開発 PC): Demucs 1 窓 = WebGPU 約 200ms / WASM 約 2 秒。1 秒ぶんの分離 + 解析で約 570ms (GPU)。出力の遅れは約 4 秒
- オフライン版 (Python で分離) とのメロディ一致率 87%、ベース 68% (なんもねえ 冒頭 50 秒)
- 画面のピアノロール・レジスタ表示は変換した時点で出るので、音より数秒早く動く
- 分離モデルは「高精度 (htdemucs_ft)」が既定: 音ごとに専用のモデル 4 つ (各 174MB)。GPU のときだけ使え、2 秒ごとに分離 (2 秒ぶんを約 1.5 秒)、出力の遅れ約 4.8 秒。
  作り方: `for i in 0 1 2 3; do .tools/venv/Scripts/python.exe tools/export-demucs.py models/htdemucs_ft_$i.onnx htdemucs_ft $i; done`
- 読み込み時に 1 回空運転して、GPU の初回の遅さで出力の遅れが延びないようにしている
- ラズパイでは GPU が無いので、Demucs の軽量化 (小さいモデル・量子化) か、AI 用の拡張ボードが必要になる見込み

## 高精度フル曲 MIDI 変換 (GPU フル活用・2 パス一括)

リアルタイム制約 (遅延・計算量の上限) を外し、曲全体を丸ごと解析してから 2 パスで最高精度のファミコン MIDI アレンジを行うモードです (`worklet/midi-arranger.js`, `worklet/midi-export.js`)。

1. **全曲 DP ビート＆小節頭推定**: 曲全体のドラム・立ち上がりから BPM と 4/4 の小節頭を大域最適化
2. **全曲ビタビ調 (転調含む)・場面判定**: 小節単位で 24 調と「静か / 普通 / サビ」を判定
3. **7th / sus4 対応の全曲コード進行**: 機能和声 + ベース一致で 72 種のコード進行を大域ビタビ推定
4. **16 分音符グリッド MIDI 採譜**: 矩形波1 (歌/リード)、矩形波2 (楽器カウンターメロディ / 8分伴奏 / 16分アルペジオ)、三角波 (8分オクターブベース)、ドラム (クラッシュ・オープンハット・8分ハイハット) を離散 MIDI ノート化し、2A03 APU 波形 + `.mid` + 21 バイト/フレーム `.bin` を生成

### ブラウザで使う (WebGPU)
1. `node server.js` で起動し、**「音源分離 + AI 解析 (Demucs)」** にチェックを入れる (GPU では `htdemucs_ft` が既定)
2. 音声ファイルを開き、**「★ 高精度フル曲MIDI変換」** をクリック (「一括分離の精度」で `shifts=2 / 4` を選択可能)
3. 完了すると原音と **遅延 0** で完全同期再生され、**MIDI 保存 (.mid)** / **WAV 保存 (.wav)** / **保存 (.bin)** で書き出せます。分離・AI 解析結果はキャッシュされるため、スライダーを変えて再変換するときは数秒で終わります

### CLI で最高精度を使う (CUDA / DirectML / CoreML GPU)

GPU 搭載 PC では PyTorch (CUDA/MPS) と ONNX Runtime (CUDA/DirectML/CoreML) を自動検出し、1 コマンドで最高精度の音源分離 → AI 採譜 → MIDI 編曲 → 2A03 合成を実行できます。

```bash
# GPU 最高精度 (htdemucs_ft + overlap 0.5 + shifts 4)
node tools/hq-arrange.mjs song.mp3 --out hq-out

# 6 ステム分離 (guitar / piano も分離)
node tools/hq-arrange.mjs song.mp3 --model htdemucs_6s --shifts 4 --out hq-out

# 歌だけ BS-RoFormer で最高精度分離 (要: pip install audio-separator[gpu])
node tools/hq-arrange.mjs song.mp3 --roformer --out hq-out
```

`hq-out/` に `chip.wav` (2A03 音声)、`arrangement.mid` (SMF Format 1)、`fc-regs.bin` (21 バイト/フレーム)、`dpcm-c000.bin` ($C000 DPCM バンク)、`summary.json` が出力されます。

## DPCM ドラム

キック・スネアは DMC チャンネルで短いサンプル (1 ビットデルタ, 約 33.1kHz) を鳴らします (「ドラム」で切替)。
三角波をキックに使わなくなるので、ベースが途切れません。ハイハットとスネアのアタックはノイズで重ねます。

- サンプルは `worklet/dpcm.js` で合成 → 1 ビットデルタに変換し、`$C000` からの 16KB バンクに並べる (現在 1.6KB 使用)
- 「DPCM バンク保存」で `dpcm-c000.bin` (16KB) を出力。カートリッジの `$C000-$FFFF` にそのまま置く
- DMC はカートリッジの `$C000-$FFFF` しか読めないので、サンプルは必ずカートリッジ側に置く必要がある

## レジスタログ (.bin) の形式

「記録開始」→「保存」で、1 フレーム (1/60 秒) あたり **21 バイト**の列を出力します。

| オフセット | 内容 |
|---|---|
| 0–19 | `$4000`–`$4013` の値 |
| 20 | 書き込みマスク: bit0=`$4003`, bit1=`$4007`, bit2=`$400B`, bit3=`$400F`, bit4=DPCM 発音 |

再生側は毎フレーム (NMI) で次の順に書きます。

1. `$4000`–`$400E` のうち `$4003/$4007/$400B` 以外を書く
2. マスク bit0–3 が立っていれば `$4003/$4007/$400B/$400F` を書く (位相リセットを起こすので必要なときだけ)
3. マスク bit4 が立っていれば `$4011`, `$4010`, `$4012`, `$4013` を書き、`$4015 = $0F` → `$4015 = $1F` (DPCM を頭から再生)

初期化時に `$4015 = $0F`, `$4001 = $4005 = $08` を書いてください。

## 実機 (カートリッジ経由) の構成案

```
Bluetooth 音声 → [Raspberry Pi] 解析 (engine/driver) → 1 フレーム 21 バイト
                        │ SPI / USB
                        ▼
              [RP2040 (Raspberry Pi Pico)] PIO で 6502 バスに応答 (5V⇔3.3V はレベル変換)
                        │ カートリッジ端子
                        ▼
              [ファミコン] 6502 が再生ルーチンを実行 → 2A03 APU が発音
```

ラズパイ (Linux) から 1.79MHz の CPU バスに直接応答するのは難しいので、バスの応答はマイコン (RP2040 の PIO など) に任せる。
カートリッジ側に見せるメモリ:

| アドレス | 内容 |
|---|---|
| `$6000-$6014` | ラズパイが毎フレーム書き換える 21 バイト (メールボックス) |
| `$8000-$BFFF` | 再生ルーチン (NMI ごとにメールボックスを APU へコピーするだけ) |
| `$C000-$FFFF` | DPCM サンプル (`dpcm-c000.bin`) + 割り込みベクタ |

再生ルーチンは、上の「レジスタログの形式」の手順をメールボックスに対して行うだけ (100 バイト程度の 6502 コード)。
フレームの取りこぼしを防ぐには、メールボックスを 2 面にするか、数フレーム分の FIFO にする。

日本のファミコンはカートリッジの音声入出力端子を通るので、将来 **拡張音源** (VRC6 / Namco 163 など) を足すこともできる。

## 実機に向けたロードマップ (案)

1. **再生ルーチン + テスト ROM**: レジスタログ (.bin) と DPCM バンクを入れた NROM/MMC3 の ROM を作り、エミュレーターと実機で鳴らして確認
2. **カートリッジ化**: 上の構成でメールボックスをリアルタイムに更新
3. **ラズパイで解析**: engine/driver をそのまま Node で動かし (または移植)、AI 解析は onnxruntime (ARM) で。
   ラズパイでは AI 解析の推論間隔を広げる・モデルを軽量化するなどの調整が必要になる見込み

## 実機での注意点
- ピッチベンドで周期の上位ビット ($4003/$4007) が変わる瞬間は、実機では位相リセットで小さなプツ音が出ます
  (周期 256/512/1024 の境目 ≒ A4・A3・A2 付近)。必要ならスイープユニットを使った回避策を再生側に入れます。

## 既知の制限
- 歌が中央にない曲 (古いステレオ録音など) ではボーカルモードの効果が薄い
- 和音が多い曲では、ハモリのパートが落ち着かないことがある (「安定度」を上げると落ち着きます)
- ハイハットは他の音に埋もれると拾いにくい
- DPCM の音量は変えられない (実機の仕様)。強弱は重ねるノイズの音量だけで表現
- E1 より低い音は検出対象外
